# 國際化（i18n）

Angular 的*國際化*（*i18n*）工具能幫助你讓應用程式支援多種語言。

試試這個 <live-example name="i18n" title="i18n Example in Spanish">即時範例</live-example>，它是一個翻譯成西班牙文的 JIT 編譯應用程式。

{@a angular-i18n}

## Angular 與 _i18n_ 範本翻譯

應用程式國際化是一項充滿挑戰、多面向的工作，需要投入與長期的承諾。
Angular 的 _i18n_ 國際化設施可以提供幫助。

本頁說明可用來協助將元件範本文字翻譯成多種語言的 _i18n_ 工具。

<div class="l-sub-section">

國際化的實務工作者將可翻譯文字稱為「_message_」。
本頁將「_text_」與「_message_」兩詞交替使用，並組合使用為「_text message_」。

</div>

_i18n_ 範本翻譯流程有四個階段：

1. 標記元件範本中的靜態文字訊息以供翻譯。

1. Angular _i18n_ 工具將標記的訊息擷取至業界標準的翻譯來源檔案。

1. 翻譯人員編輯該檔案，將擷取的文字訊息翻譯成目標語言，
然後將檔案交還給你。

1. Angular 編譯器匯入已完成的翻譯檔案，
以翻譯後的文字取代原始訊息，並以目標語言產生應用程式的新版本。

你需要為每種支援的語言，分別建置並部署應用程式的一個獨立版本。

## 處理單數與複數

不同的語言有不同的複數化規則。

假設你的應用程式要談論一群狼的數量。
在英文中，依據狼的數量，你可以顯示 "no wolves"、"one wolf"、"two wolves" 或 "a wolf pack"。
其他語言可能以不同的方式表達*基數*。

以下是你如何標記元件範本，以顯示適合狼數量的詞句：

<code-example path="i18n/src/app/app.component.html" region="i18n-plural" title="src/app/app.component.html" linenums="false">
</code-example>

* 第一個參數是 key。它繫結到決定狼數量的元件屬性（`wolves`）。
* 第二個參數將其標識為 `plural` 翻譯類型。
* 第三個參數定義一個複數化模式，由複數化類別與其對應值組成。

複數化類別包括：

* =0 (or any other number)
* zero
* one
* two
* few
* many
* other

在複數化類別旁邊的大括號（`{}`）中放入預設的*英文*翻譯。

* 當你談論一隻狼時，你可以寫 `=1 {one wolf}`。

* 對於零隻狼，你可以寫 `=0 {no wolves}`。

* 對於兩隻狼，你可以寫 `=2 {two wolves}`。

你可以為三隻、四隻以及其他任何數量的狼一直這樣寫下去。
或者，你可以將 **`other`** 類別指定為所有不相符基數的萬用類別，並寫成像這樣：`other {a wolf pack}`。

<div class="l-sub-section">

這個語法符合
<a href="http://userguide.icu-project.org/formatparse/messages" title="ICU Message Format">ICU Message Format</a>，
它源自
<a href="http://cldr.unicode.org/" title="CLDR">Common Locale Data Repository (CLDR)</a>，
後者規範了
<a href="http://cldr.unicode.org/index/cldr-spec/plural-rules" title="Pluralization Rules">複數化規則</a>。

</div>

## 使用 _ng-xi18n_ 工具建立翻譯來源檔案

使用 **_ng-xi18n_ 擷取工具，**將標示有 `i18n` 的文字擷取至業界標準格式的翻譯來源檔案。

這是一個 Angular CLI 工具，位於 `@angular/compiler-cli` npm 套件中。
如果你尚未安裝 CLI 及其 `platform-server` 對等相依性，請立即安裝：

<code-example language="sh" class="code-shell">
  npm install @angular/compiler-cli @angular/platform-server --save
</code-example>

在應用程式專案的根目錄開啟終端機視窗，並輸入 `ng-xi18n` 指令：

<code-example language="sh" class="code-shell">
  ./node_modules/.bin/ng-xi18n
</code-example>

<div class="l-sub-section">

Windows 使用者可能需要像這樣為指令加上引號：`"./node_modules/.bin/ng-xi18n"`

</div>

預設情況下，該工具會產生一個名為 **`messages.xlf`** 的翻譯檔案，採用
<a href="https://en.wikipedia.org/wiki/XLIFF">XML Localization Interchange File Format (XLIFF, version 1.2)</a>。

{@a other-formats}

### 其他翻譯格式

Angular i18n 工具支援 XLIFF 1.2 與 XLIFF 2，以及
<a href="http://cldr.unicode.org/development/development-process/design-proposals/xmb" >XML Message Bundle (XMB)</a>。

你可以如這些範例指令所示，使用 `--i18nFormat` 旗標*明確*指定你選擇的格式

<code-example language="sh" class="code-shell">
./node_modules/.bin/ng-xi18n  --i18nFormat=xlf  --outFile=messages.xlf
./node_modules/.bin/ng-xi18n  --i18nFormat=xlf2 --outFile=messages.xliff2.xlf
./node_modules/.bin/ng-xi18n  --i18nFormat=xmb  --outFile=messages.xmb
</code-example>

*本*指南中的範例使用預設的 *XLIFF 1.2* 格式。

{@a ng-xi18n-options}

### 其他選項

你可能需要指定額外的選項。
例如，如果 `tsconfig.json` TypeScript 設定檔位於根資料夾以外的位置，
你必須使用 `-p` 選項標識它的路徑：

<code-example language="sh" class="code-shell">
  ./node_modules/.bin/ng-xi18n -p path/to/tsconfig.json
  ./node_modules/.bin/ng-xi18n  --i18nFormat=xmb -p path/to/tsconfig.json
</code-example>

{@a npm-i18n-script}

### 新增便於使用的 _npm_ 腳本

請考慮在 `package.json` 的 `scripts` 區段中加入一個便捷的捷徑，讓指令更容易記住與執行：

<code-example format='.' language='sh'>
  "scripts": {
    "i18n": "ng-xi18n",
    ...
  }
</code-example>

現在你可以發出像這樣的指令變化形式：

<code-example language="sh" class="code-shell">
  npm run i18n
  npm run i18n -- -p path/to/tsconfig.json
  npm run i18n -- --i18nFormat=xmb -p path/to/tsconfig.json
</code-example>

請注意選項之前的 `--` 旗標。
它告訴 *npm* 將其後的每個旗標都傳給 `ng-xi18n`。

## 翻譯文字訊息

一種做法是專門用一個資料夾來進行在地化，並將相關資產（例如國際化檔案）儲存在那裡。

## 翻譯 _plural_ 與 _select_
翻譯 _plural_ 與 _select_ 訊息有一點棘手。

對於 `plural` 與 `select` 翻譯單位，`<source>` 標籤是空的，這使它們難以與原始範本對應。
`XLIFF` 格式尚未支援 ICU 規則。
不過，`XMB` 格式確實支援 ICU 規則。

你只能參照來源範本其他位置中你能辨識的翻譯單位，來尋找它們。

## 將已完成的翻譯檔案合併至應用程式中

若要將已翻譯的文字合併至元件範本中，請使用已完成的翻譯檔案來編譯應用程式。
無論該檔案是 `.xlf` 格式，還是 Angular 能理解的其他格式（例如 `.xtb`），流程都相同。

你需要為 Angular 編譯器提供三項新資訊：

  * 翻譯檔案。
  * 翻譯檔案的格式。
  *   <a href="https://en.wikipedia.org/wiki/XLIFF">_Locale ID_</a>
  （例如 `es` 或 `en-US`）。

你提供這些資訊的方式，取決於你是用 JIT（*Just-in-Time*）編譯器還是 AOT（*Ahead-of-Time*）編譯器進行編譯。

  * 使用 [JIT](guide/i18n#jit) 時，你會在啟動時提供該資訊。
  * 使用 [AOT](guide/i18n#aot) 時，你會將該資訊以 `ngc` 選項的形式傳遞。

有三個提供者會告訴 JIT 編譯器，在編譯應用程式時如何翻譯特定語言的範本文字：

* `TRANSLATIONS` 是包含翻譯檔案內容的字串。
* `TRANSLATIONS_FORMAT` 是檔案的格式：`xlf`、`xlf2` 或 `xtb`。
* `LOCALE_ID` 是目標語言的地區設定。

以下 `src/app/i18n-providers.ts` 中的 `getTranslationProviders()` 函式，會依據使用者的*地區設定*與對應的翻譯檔案建立那些提供者：

1. 它從 `index.html` 中設定的全域 `document.locale` 變數取得地區設定。

1. 如果沒有地區設定，或者語言是美國英文（`en-US`），就不需要翻譯。
  該函式會以 `Promise` 的形式回傳一個空的 `noProviders` 陣列。

### 使用 AOT 編譯器進行 _國際化_

JIT 編譯器會在瀏覽器中動態編譯應用程式的同時，將它翻譯成目標語言。
這很靈活，但對你的使用者而言可能不夠快。

AOT（*Ahead-of-Time*）編譯器是一個建置流程的一部分，該流程會產生一個小型、快速且可立即執行的應用程式套件。
當你使用 AOT 編譯器進行國際化時，你會為每種語言預先建置一個獨立的應用程式套件。接著，在主機網頁（在此例中為 `index.html`）中，你判斷使用者需要哪種語言，並提供適當的應用程式套件。

本指南不涵蓋如何建置多個應用程式套件並依據使用者的語言偏好提供它們。
它確實說明了告訴 AOT 編譯器套用翻譯檔案所需的幾個步驟。

使用 AOT 編譯器進行國際化，需要專門為 AOT 編譯進行一些設定。
從[即將合併翻譯檔案之前](guide/i18n#app-pre-translation)所示的應用程式專案開始，並參閱 [AOT 指南](guide/aot-compiler)使它達到 *AOT 就緒*狀態。

接著，為每種支援的語言（包括英文）發出一個 `ngc` 編譯指令。
結果是每種語言都有一個獨立版本的應用程式。

透過為 `ngc` 指令加入三個選項，告訴 AOT 如何翻譯：

  * `--i18nFile`：翻譯檔案的路徑。
  * `--locale`：地區設定的名稱。
  * `--i18nFormat`：在地化檔案的格式。

對於這個範例，西班牙文指令會是：

<code-example language="sh" class="code-shell">
  ./node_modules/.bin/ngc --i18nFile=./locale/messages.es.xlf --locale=es --i18nFormat=xlf
</code-example>

<div class="l-sub-section">

Windows 使用者可能需要為指令加上引號：

<code-example language="sh" class="code-shell">
  "./node_modules/.bin/ngc" --i18nFile=./locale/messages.es.xlf --locale=es --i18nFormat=xlf
</code-example>

</div>

如果你忘記提供翻譯，建置會成功，但會產生一個你可能很容易忽略的警告。

* Error
* Warning (default)
* Ignore

{@a maintenance}

## 檔案維護與 _id_ 變更

隨著應用程式演進，你會變更 _i18n_ 標記，並多次重新執行 `ng-xi18n` 擷取工具。
你加入的*新*標記不是問題。
但 `id`*可能是一個嚴重的問題！*

如果 `id` 是由工具產生的，對*現有*標記的*大多數*變更，都會導致工具為受影響的翻譯單位產生一個*新的* `id`。

在 `id` 變更後，翻譯檔案就不再同步。
正因如此，你在重新編譯時會收到一些警告訊息。
這些警告訊息會指出某些翻譯遺失，但不會告訴你哪些舊 `ids` 已不再有效。

如果你使用[自訂 id](#custom-id "Set a custom id")，工具會在你變更對應翻譯單位時保留自訂 `id`。**除非你有很好的理由，否則請一律使用自訂 _ids_。**

無論你使用產生的還是自訂的 `ids`，**請一律將所有翻譯訊息檔案提交至版本控制，**尤其是英文來源 `messages.xlf`。
新舊 `messages.xlf` 檔案之間的差異，將幫助你在所有翻譯檔案中找到並更新 `ids` 與其他變更。
